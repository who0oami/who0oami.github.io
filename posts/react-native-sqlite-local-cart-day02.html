장바구니는 휴대폰에,
주문은 서버에

장바구니를 고치려고 할 때마다 서버가 필요했다. 사용자가 인터넷 없이도 상품을 담을 수 있으려면, 어떤 데이터를 휴대폰에 남겨야 할까?

2026.11.13 · 유지현 · Day 02 · 6 min read

장바구니를 왜 서버에만 두었을까

첫 버전의 Cup & Go는 서버의 JSON 파일에 장바구니와 주문을 함께 보관했다. 앱은 익명 사용자 ID만 저장하고 상품을 담거나 수량을 바꿀 때 서버에 요청했다. 서버를 끄면 장바구니도 수정할 수 없었다. 메뉴를 조회할 때 인터넷이 필요한 건 자연스럽지만, 이미 담아 둔 상품의 수량까지 항상 서버에 물어야 할 필요가 있을까?

MySQL을 붙이면 더 실제 서비스처럼 보일 수는 있다. 하지만 먼저 결정할 것은 DB 제품이 아니라 누가 언제 그 데이터를 사용하고 책임지는지였다. 아직 결제가 없는 학습용 앱이니, 장바구니는 사용자 기기에서 관리하고 주문 확정 정보만 서버가 책임지는 구조를 택했다.

두 개의 SQLite, 서로 다른 책임

  • 모바일 앱 — Expo SQLite의 cart_items에 메뉴 정보와 수량을 저장하도록 구현했다. 앱을 다시 실행했을 때 읽어오는 흐름을 설계했다.
  • 웹 데모 — 브라우저 환경에는 별도 AsyncStorage 저장 방식을 사용한다. 모바일 SQLite와 같은 구현이라고 보지는 않는다.
  • 서버 — Node.js node:sqlite의 orders 테이블에 주문 기록을 저장한다. 메뉴 조회 GET과 주문 생성 POST를 제공한다.
src/services/cart-sql.ts · SQL excerpt
INSERT INTO cart_items (item_id, item_json, quantity)
VALUES (?, ?, ?)
ON CONFLICT(item_id) DO UPDATE SET
  item_json = excluded.item_json,
  quantity = MIN(20, cart_items.quantity + excluded.quantity);

같은 메뉴를 두 번 담으면 행을 늘리지 않고 수량을 합친다. 수량 상한은 20개로 두고, 문자열을 SQL에 직접 붙이는 대신 바인딩 파라미터를 사용했다. 화면 컴포넌트는 SQL 문을 알 필요가 없도록 장바구니 Context와 저장소 모듈을 구분했다.

주문 가격은 서버가 다시 계산했다

휴대폰 DB에 저장된 가격은 변경될 수 있다. 화면에 표시된 총액을 그대로 신뢰해서 주문을 확정하면 요청 내용에 따라 금액이 달라질 수도 있다. 그래서 POST 주문 요청에는 메뉴 ID와 수량을 보내고, 서버가 자신의 메뉴 목록 기준으로 가격을 다시 계산하도록 했다.

주문 성공 응답을 받은 뒤에만 로컬 장바구니를 비운다. 오류가 나면 담아 둔 상품은 남겨둔다. 같은 주문 요청을 다시 보낼 때 중복 주문이 생기지 않도록 클라이언트 ID와 요청 ID 조합을 고유하게 관리하는 로직도 넣었다.

코드에서 확인한 것과 아직 확인하지 못한 것

서버 SQLite 테스트에서는 주문 기록 유지, 동일 요청 재시도 시 중복 방지, 서버 가격 재계산 등을 확인했다. 로컬 장바구니 SQL에 대해서는 중복 메뉴 수량 합산, 수정·삭제와 잘못된 수량의 처리를 점검했다.

반면 실제 iOS·Android 시뮬레이터에서 앱 설치·재실행을 검증한 결과는 아직 없다. 작업 환경의 패키지 설치 제약으로 Expo SQLite 네이티브 빌드를 끝내지 못했다. Mac에서 빌드한 뒤 앱 강제 종료·재실행, 오프라인 수량 수정, 서버 연결 복구 후 주문을 다시 확인해야 한다.

이번 변경에서 배운 것

로컬 SQLite를 사용한다고 서버 DB가 필요 없어진 것은 아니다. 장바구니처럼 기기에서 즉시 수정해야 하는 데이터와, 주문처럼 여러 시스템이 공유하고 책임져야 하는 데이터는 성격이 다르다. DB를 더 많이 쓰는 것보다 저장 위치의 경계를 설명할 수 있는 구조가 중요하다는 걸 배웠다.

다음은 Mac에서 양쪽 시뮬레이터를 직접 실행하고, 재실행·오프라인·오류 복구 흐름을 화면으로 검증하는 작업이다. 아직 확인되지 않은 부분은 결과로 포장하지 않고 체크리스트에 남겨둔다.
