3분 영상이 나오기까지 33분이 걸렸다

변환은 성공했지만 기다리기에는 너무 길었다. 어디서 시간이 새는지 직접 재고, Render 무료 서버에서 8분 27초까지 줄였다.

2026.10.08 · 유지현 · 9 min read

완료는 떴는데 33분이 지나 있었다

YouTube 자막도 가져왔고, Gloss와 수어 Asset도 제대로 매칭됐다. 끝까지 실행하면 결과 영상도 나왔다. 다만 약 3분짜리 영상을 한 번 만드는 데 33분이 걸렸다. Render 무료 인스턴스는 0.1 CPU, 512MB라 로컬에서 괜찮았던 코드가 그대로 버티지 못했다.

일단 시간을 나눠서 재봤다

처음에는 Gemini 호출이 느린 줄 알았다. 자막, Gloss, S3, Timeline, FFmpeg 앞뒤에 시간을 찍어 보니 예상이 틀렸다. 같은 수어 클립을 계속 ffprobe로 읽고, 이미 규격이 맞는 영상까지 다시 인코딩하는 구간이 대부분을 차지했다.

1. 준비된 클립을 다시 인코딩하지 않기

S3 클립은 이미 1080p, 30fps, 무음으로 맞춰져 있었다. 그런데 합칠 때마다 전부 다시 인코딩하고 있었다. ffprobe로 꼭 필요한 항목만 확인하고 규격이 맞으면 -c copy로 바로 연결했다. 가장 큰 시간 절약은 새로운 알고리즘이 아니라 쓸데없는 작업을 빼는 데서 나왔다.

video merger optimization · simplified
ready = is_clip_concat_ready(probe_clip(src, probe_cache))
normalized_cache[src] = src if ready else normalize_clip(src)

# 이미 같은 규격이면 디코딩·인코딩 없이 컨테이너만 연결한다.
ffmpeg("-f concat -safe 0 -c copy")

2. 같은 작업을 캐시하기

같은 수어 단어가 여러 번 등장할 때마다 메타데이터 조회와 정규화를 반복하지 않도록 Job 단위 캐시를 만들었다.

  • ffprobe 결과 캐시
  • 정규화된 클립 캐시
  • 같은 길이의 Idle 영상 캐시
  • 중복 WORD Asset 다운로드 방지

3. FFmpeg 실행 횟수 줄이기

각 단어와 Segment마다 별도 프로세스를 실행하면 저사양 CPU에서는 프로세스 생성 비용도 무시할 수 없었다. 인접한 수어 구간을 묶고, Segment 내부 클립을 먼저 연결한 뒤 최종 결과를 한 번 더 합치는 구조로 바꿨다.

4. 무료 인스턴스에서 안전하게 실행하기

속도만 높이고 동시에 여러 Job을 렌더링하면 512MB 메모리를 넘을 수 있었다. 렌더링 동시 실행은 하나로 제한하고, FFmpeg에는 ultrafast, 단일 thread, timeout을 적용했다. ffprobe의 패킷 전체 조회도 제거했다.

결과 파일도 S3로 이동했다

Render의 로컬 디스크에 만든 MP4는 재배포 시 사라졌다. DB에는 완료로 남지만 재생 URL은 404가 됐다. 완성 파일을 S3의 results/{job_id}.mp4에 업로드하고 Backend API가 서명 URL로 리다이렉트하도록 변경했다.

backend/services/result_storage.py
key = f"results/{job_id}.mp4"
s3.upload_file(path, bucket, key, ExtraArgs={"ContentType": "video/mp4"})

return s3.generate_presigned_url(
    "get_object", Params={"Bucket": bucket, "Key": key}
)

배포 환경에서 함께 해결한 문제

Render 서버 IP에서는 YouTube 자막 조회가 차단될 수 있었다. 해당 오류만 감지해 Gemini가 공개 영상의 음성을 직접 전사하도록 Fallback을 추가했다. 로컬의 AWS CLI 프로필도 컨테이너에는 없기 때문에 Render에서는 환경변수 기반 인증을 우선 사용했다.

다시 돌려 보니 8분 27초가 걸렸다

처음 측정에 쓴 약 3분 영상을 그대로 넣었다. 전체 처리 시간은 33분에서 8분 27초로 줄었고, 메모리 초과 없이 S3 업로드까지 끝났다. 영상 API의 307 리다이렉트와 실제 video/mp4 응답도 함께 확인했다.

결국 무료 서버에서 효과가 가장 컸던 건 코드를 더 빠르게 실행하는 방법보다, 반복하던 인코딩과 메타데이터 조회를 없애는 일이었다.
