예쁜 화면보다 실패하는 API부터

React Native로 카페 주문 앱의 세 화면을 만들었다. 메뉴가 잘 보이는 것보다, 메뉴를 불러오지 못했을 때 앱이 어떻게 반응하는지 먼저 확인했다.

2026.11.12 · 유지현 · Day 01 · 7 min read

왜 또 하나의 카페 주문 앱을 만들었나

Flutter와 SwiftUI에서는 모바일 화면과 FastAPI 서버를 연결해본 적이 있다. 하지만 React Native는 다른 방식으로 컴포넌트와 상태를 다룬다. 소프트웨어 개발 일경험 JD에 RN 전환, API 연동, QA, 코드리뷰가 명시돼 있어 가장 기본적인 기능부터 확인해 보기로 했다. 메뉴 목록, 메뉴 상세, 장바구니. 이름은 Cup & Go로 정했다.

AI 코딩 도구의 도움으로 구현을 진행했지만, 단순히 화면을 완성했다는 기록으로 끝내고 싶지 않았다. 어떤 데이터를 어디에서 관리할지, 실패하는 요청은 어떻게 안내할지, 무엇을 테스트했는지 설명 가능한 구조가 목표였다.

화면에서 API 호출을 분리했다

화면 안에 HTTP 요청, 로딩 상태, 오류 메시지까지 모두 넣으면 수정 범위가 불필요하게 커진다. 메뉴 요청은 services/menu-api.ts, 비동기 상태는 hooks/use-menu.ts, 렌더링은 화면 컴포넌트에 두었다. 카테고리 필터와 검색은 이미 받아 온 목록에 적용했다.

src/hooks/use-menu.ts · excerpt
useEffect(() => {
  const controller = new AbortController();
  getMenu(controller.signal)
    .then(items => {
      if (!controller.signal.aborted) {
        setState({ items, loading: false, error: null });
      }
    })
    .catch(error => {
      if (!controller.signal.aborted) {
        setState(current => ({
          ...current, loading: false,
          error: error instanceof Error ? error.message : '요청 실패'
        }));
      }
    });
  return () => controller.abort();
}, [requestId]);

AbortController는 화면이 떠난 뒤 이전 응답이 늦게 도착해 상태를 바꾸는 문제를 피하기 위해 넣었다. 재시도 동작도 별도 상태로 관리하도록 했다.

실패 응답을 의도적으로 만들었다

외부 API의 상태에 테스트가 좌우되지 않도록 Node.js로 메뉴 조회용 모의 API를 만들었다. GET /menu는 메뉴 데이터를, ?fail=1은 의도적인 HTTP 503 응답을 반환한다. 서버가 꺼져 있는 경우와 오류 응답을 받는 경우 모두 사용자에게 안내하고 다시 시도할 수 있도록 했다.

  • 정상 요청: 메뉴 일곱 개 표시
  • 로딩: 요청 중 상태를 분리해 표시
  • 오류: 실패 원인을 안내하고 재시도 제공
  • 장바구니: 수량 합산과 총액 계산을 순수 함수로 분리해 검사

iOS와 Android에서 localhost가 다른 이유

iOS 시뮬레이터와 웹에서는 개발 머신의 localhost:4000을 사용할 수 있다. 반면 Android 에뮬레이터의 localhost는 에뮬레이터 자신이기 때문에 호스트를 가리키는 10.0.2.2:4000을 기본값으로 분기했다. 실제 휴대전화에서는 Mac과 같은 네트워크의 LAN IP가 필요하다.

이 부분은 코드와 실행 안내에 반영했지만, 실제 iOS·Android 시뮬레이터 실행은 아직 검증하지 않았다. 실행하도록 코드를 구성한 것과 기기에서 검증했다는 것은 구분해서 기록할 생각이다.

결과와 다음 단계

초기 버전에서는 TypeScript 검사, ESLint 검사, Node 자동 테스트 6개, Expo 웹 번들 생성을 확인했다. 하지만 이 결과만으로 네이티브 UI 동작까지 증명할 수는 없다. 다음으로 장바구니의 저장 위치를 다시 정하고, 화면 전환과 앱 재실행 시나리오를 점검하려 한다.

작은 앱을 만들면서도 결국 중요한 건 데이터가 정상적으로 들어올 때보다 들어오지 않을 때의 흐름이었다. 화면 하나라도 실패 조건과 상태 관리까지 설명할 수 있도록 만들고 싶다.
