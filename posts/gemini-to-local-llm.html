Gemini 대신 직접 모델을 만들면 될까?

API 비용이 부담돼 mT5부터 학습해 봤다. 잘되지 않았고, 그다음에는 Ollama/Qwen을 붙였다. 어디서 실패했고 무엇을 남겼는지 정리했다.

2026.10.08 · 유지현 · 10 min read

시작은 API 비용 문제였다

초기 파이프라인은 Gemini에 한국어 자막을 보내 KSL Gloss 배열을 받았다. MVP를 확인하기에는 빨랐지만, 영상 하나가 여러 Segment로 나뉘면서 테스트할 때마다 호출이 쌓였다. 과금과 quota를 신경 쓰다 보니 마음 놓고 반복하기도 어려웠다.

“그러면 작은 모델을 직접 학습하면 되지 않을까?”라는 생각으로 시작했다. Backend가 받는 list[str] 형태는 그대로 두고, Gemini 자리에 로컬 변환기를 끼우는 게 목표였다.

첫 번째 시도: mT5 파인튜닝

한국어 문장을 입력하고 Gloss 토큰 시퀀스를 출력하는 seq2seq 문제로 정의했다. mT5-small을 사용하고 한정된 장비에서도 반복할 수 있도록 batch size 1, gradient accumulation, Adafactor 중심의 저메모리 학습 파이프라인을 만들었다.

  • 입력: 한국어 문장
  • 출력: Gloss를 전용 구분자로 연결한 문자열
  • 검증: 저장된 모델을 새 객체로 다시 로드한 뒤 추론
  • 평가: 예측과 정답의 Gloss token F1

학습이 끝났다는 로그만으로 성공으로 판단하지 않았다. 가중치를 디스크에 저장하고 다시 불러온 모델이 빈 결과나 특수 토큰을 내지 않는지 확인하고, 최소 F1 기준을 넘을 때만 검증 결과를 남기도록 했다.

학습은 끝났지만 서비스에는 못 넣었다

코드는 돌았고 모델 파일도 만들어졌다. 하지만 처음 보는 문장을 넣으면 빈 결과나 어색한 토큰이 자주 나왔다. 한국어를 KSL 어순으로 바꾸는 일과 보유 Asset 안에서 표현하는 일을 같이 학습시키기에는 문장–Gloss Pair가 부족했다.

여기서 학습 완료 로그를 성공 기준으로 삼으면 안 된다는 걸 확인했다. 저장한 모델을 새 객체에서 다시 불러 실제 문장을 넣어 봐야 했다. 제한된 데이터로 학습 횟수만 늘리기보다, 이미 한국어를 이해하는 로컬 LLM에 KSL 규칙과 Asset 제약을 주는 쪽으로 다음 실험을 바꿨다.

두 번째 시도: Ollama/Qwen

다음에는 Ollama에서 Qwen 2.5 3B를 돌렸다. 이미 한국어를 어느 정도 이해하는 모델이라 규칙을 프롬프트로 주는 편이 적은 데이터로 mT5를 계속 학습하는 것보다 결과가 안정적이었다. API 비용 없이 같은 문장을 반복해서 비교할 수 있다는 점도 컸다.

프롬프트에 넣은 제약

  • 한국어 문장을 KSL 어순의 Gloss 배열로 반환
  • 조사와 불필요한 활용 제거
  • 부정 표현과 복합 표현 정규화
  • 보유한 allowed_words를 우선 사용
  • 미지원 고유명사와 단어는 삭제하지 않고 캡션으로 유지

형식이 맞더라도 원문의 핵심 의미가 사라질 수 있어 간단한 의미 검증 단계도 추가했다. 검증을 통과하지 못한 Segment는 억지로 잘못된 수어 클립에 연결하는 대신 원문 캡션으로 복구했다.

출력 형식을 좁히고, 의미는 다시 검사했다

Qwen에는 WORD ID 생성을 맡기지 않았다. 모델은 한국어 사전형 Gloss 배열만 반환하고, 실제 Asset 코드는 기존 Matcher가 결정한다. 출력은 JSON으로 강제하고 temperature를 0으로 고정했다. 영어·한자·설명문이 섞이거나 부정과 수량이 사라지면 한 번만 재생성한 뒤 실패로 처리했다.

local LLM validation flow · simplified
body = {
    "model": "qwen2.5:3b",
    "format": "json",
    "options": {"temperature": 0, "top_p": 0.9},
}

glosses = normalize_observed_forms(source, parsed_glosses)
issues = validation_issues(source, glosses)
if issues:
    regenerate_once(source, issues)

하나를 선택하는 대신 Provider로 분리했다

Gemini는 배포 안정성이 높고, Local LLM은 비용 없이 실험하기 좋으며, mT5는 데이터가 충분해졌을 때 다시 개선할 가치가 있었다. 하나의 구현을 지우지 않고 환경변수로 변환기를 선택하도록 통합했다.

  • gemini: 현재 배포 기본값
  • local: Ollama/Qwen 비교·개발 환경
  • mt5: 파인튜닝 모델 평가 환경

세 구현은 모두 str → list[str] 계약을 유지한다. 그래서 Provider를 바꿔도 Gloss Matcher, Timeline, Frontend 코드는 수정하지 않는다. 환경변수 KSL_GLOSS_PROVIDER만 바꿔 동일한 입력을 비교할 수 있게 했다.

provider selection · simplified
provider = os.getenv("KSL_GLOSS_PROVIDER", "gemini")

if provider == "local":
    return convert_to_gloss_local(text)
if provider == "mt5":
    return convert_to_gloss_mt5(text)
return convert_to_gloss_gemini(text)

결국 Gemini를 지우지는 않았다

처음 목표였던 완전 대체에는 실패했다. 대신 Gemini, Local LLM, mT5를 같은 입력으로 바꿔 끼울 수 있게 됐다. 배포에서는 Gemini를 쓰고, 비용 없이 반복할 때는 Local LLM을 쓰며, 데이터가 더 모이면 mT5를 다시 평가할 수 있다.

실패한 학습 코드를 없애지 않은 이유도 같다. 다음 실험이 “느낌상 더 좋다”로 끝나지 않게, 같은 저장·재로딩·F1 기준으로 다시 비교할 수 있도록 남겨 뒀다.
