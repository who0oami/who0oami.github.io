Gemini에서 Local LLM까지: KSL Gloss 변환 실험

외부 API 비용을 줄이기 위해 직접 모델을 학습하고, 실패의 원인을 확인한 뒤 Ollama/Qwen으로 방향을 바꾼 기록입니다.

2026.10.08 · 7 min read

시작은 API 비용 문제였다

공농의 초기 KSL 변환 파이프라인은 Gemini API를 사용했다. 한국어 자막을 문장 단위로 보내면 KSL Gloss 배열을 얻는 방식이었다. 빠르게 기능을 검증하기에는 좋았지만 영상 하나에도 여러 Segment가 생기기 때문에 반복 테스트만으로 호출량이 크게 늘었다.

팀에서 API 과금과 quota 문제가 제기됐고, 외부 API에 의존하지 않는 변환기를 직접 만들어 보기로 했다. 목표는 같은 Backend 계약을 유지하면서 로컬 모델로 Gloss 배열을 반환하는 것이었다.

첫 번째 시도: mT5 파인튜닝

한국어 문장을 입력하고 Gloss 토큰 시퀀스를 출력하는 seq2seq 문제로 정의했다. mT5-small을 사용하고 한정된 장비에서도 반복할 수 있도록 batch size 1, gradient accumulation, Adafactor 중심의 저메모리 학습 파이프라인을 만들었다.

  • 입력: 한국어 문장
  • 출력: Gloss를 전용 구분자로 연결한 문자열
  • 검증: 저장된 모델을 새 객체로 다시 로드한 뒤 추론
  • 평가: 예측과 정답의 Gloss token F1

학습이 끝났다는 로그만으로 성공으로 판단하지 않았다. 가중치를 디스크에 저장하고 다시 불러온 모델이 빈 결과나 특수 토큰을 내지 않는지 확인하고, 최소 F1 기준을 넘을 때만 검증 결과를 남기도록 했다.

왜 서비스에 바로 적용하지 않았나

파이프라인은 동작했지만 데이터의 양과 품질이 충분하지 않았다. 일반 한국어 표현을 안정적인 KSL 어순으로 바꾸고, 동시에 서비스가 가진 Asset 목록 안에서 표현하려면 더 다양한 문장–Gloss Pair가 필요했다.

모델이 실행된다는 사실과, 서비스에서 신뢰할 수 있다는 사실은 달랐다.

제한된 데이터로 계속 학습 횟수만 늘리는 것보다, 이미 언어 능력을 가진 로컬 LLM에 KSL 규칙과 Asset 제약을 프롬프트로 전달하는 편이 현실적인 다음 실험이라고 판단했다.

두 번째 시도: Ollama/Qwen

Ollama 위에서 Qwen을 실행하고 Backend의 기존 변환 인터페이스에 연결했다. 외부 API 요청이 없어 반복 테스트 비용을 줄일 수 있었고, 프롬프트를 수정하면서 결과를 바로 비교할 수 있었다.

프롬프트에 넣은 제약

  • 한국어 문장을 KSL 어순의 Gloss 배열로 반환
  • 조사와 불필요한 활용 제거
  • 부정 표현과 복합 표현 정규화
  • 보유한 allowed_words를 우선 사용
  • 미지원 고유명사와 단어는 삭제하지 않고 캡션으로 유지

형식이 맞더라도 원문의 핵심 의미가 사라질 수 있어 간단한 의미 검증 단계도 추가했다. 검증을 통과하지 못한 Segment는 억지로 잘못된 수어 클립에 연결하는 대신 원문 캡션으로 복구했다.

하나를 선택하는 대신 Provider로 분리했다

Gemini는 배포 안정성이 높고, Local LLM은 비용 없이 실험하기 좋으며, mT5는 데이터가 충분해졌을 때 다시 개선할 가치가 있었다. 하나의 구현을 지우지 않고 환경변수로 변환기를 선택하도록 통합했다.

  • gemini: 현재 배포 기본값
  • local: Ollama/Qwen 비교·개발 환경
  • mt5: 파인튜닝 모델 평가 환경

배운 점

처음 계획했던 “API를 자체 모델로 대체한다”는 목표는 그대로 달성되지 않았다. 대신 어떤 데이터가 더 필요한지, 모델을 어떻게 검증해야 하는지, 서로 다른 변환기를 서비스 코드에 안전하게 연결하는 방법을 얻었다.

실패한 모델을 버리지 않고 재현 가능한 학습·평가 코드로 남겨두면 다음 데이터가 준비됐을 때 같은 기준으로 다시 비교할 수 있다. 이번 실험에서 가장 큰 결과는 특정 모델보다 그 비교 구조였다.
